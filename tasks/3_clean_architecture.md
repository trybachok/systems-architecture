# Задача 3. Архитектурный анализ учебной информационной системы

## 1. Что архитектурно неудачно в текущей структуре

В описанной системе бизнес-правила реализованы прямо в контроллерах и сервисах, которые завязаны на технические детали:

- HTTP-слой;
- ORM;
- SQL-запросы;
- конкретную схему базы данных;
- внешние API;
- механизмы хранения и получения данных.

Это архитектурно неудачно, потому что бизнес-логика системы оказывается смешана с инфраструктурой.

Например, правила расчета скидки, проверки права на льготы и обработки заявок являются бизнес-правилами. Они должны отражать предметную область учебной информационной системы, а не зависеть от того, через какой HTTP endpoint пришел запрос, какая ORM используется и в какой таблице лежат данные.

Проблема текущей архитектуры состоит в следующем:

```text
Контроллеры / HTTP
        |
        v
Сервисы с бизнес-логикой
        |
        v
ORM / SQL / внешние API / конкретная БД
```

На практике это означает, что изменение технических деталей приводит к изменению бизнес-логики. Например:

- изменилась схема БД — приходится менять код расчета скидки;
- поменялся внешний API — приходится переписывать обработку заявок;
- изменилась ORM — затрагиваются бизнес-правила;
- нужно протестировать расчет льготы — приходится поднимать HTTP-слой, БД или мокать ORM.

Такая структура нарушает несколько важных архитектурных принципов.

## 2. Какие принципы нарушены

### 2.1. Нарушение разделения ответственности

Контроллеры и сервисы одновременно отвечают за:

- прием HTTP-запросов;
- преобразование входных данных;
- выполнение бизнес-правил;
- работу с ORM;
- выполнение SQL-запросов;
- интеграцию с внешними API;
- формирование HTTP-ответов.

В результате один модуль знает слишком много и меняется по разным причинам.

### 2.2. Нарушение принципа инверсии зависимостей

Бизнес-логика зависит от низкоуровневых технических деталей: ORM, SQL, HTTP, внешних API.

Должно быть наоборот: бизнес-логика должна зависеть от абстракций, а инфраструктурные детали должны подключаться снаружи.

### 2.3. Нарушение тестируемости

Если расчет скидки или проверка льготы находятся внутри HTTP-контроллера или сервиса, напрямую работающего с БД, то такие правила сложно тестировать изолированно.

Для проверки бизнес-правила приходится поднимать лишнюю инфраструктуру:

- HTTP-сервер;
- тестовую БД;
- ORM;
- внешние API или их mock-версии.

Это делает тесты медленными, хрупкими и зависимыми от технических деталей.

### 2.4. Низкая устойчивость к изменениям

Система будет развиваться, требования будут меняться. Если бизнес-правила смешаны с инфраструктурой, любое изменение становится дорогим.

Изменение способа хранения данных не должно требовать переписывания правил расчета скидок. Изменение внешнего API не должно менять внутренние правила проверки права на льготу.

## 3. Какой подход здесь уместен

Для такой ситуации уместен подход **чистой архитектуры** или близкие к нему варианты:

- Clean Architecture;
- Hexagonal Architecture;
- Ports and Adapters;
- Onion Architecture.

Главная идея этих подходов: **бизнес-логика должна быть в центре системы и не должна зависеть от инфраструктуры**.

Технические детали — HTTP, ORM, SQL, БД, внешние API — должны находиться на внешнем уровне и подключаться к бизнес-логике через интерфейсы.

Целевая зависимость должна выглядеть так:

```text
HTTP / ORM / SQL / внешние API
        |
        v
Адаптеры инфраструктуры
        |
        v
Интерфейсы / порты
        |
        v
Use Cases / бизнес-сценарии
        |
        v
Domain / бизнес-правила
```

Ключевое правило:

```text
Бизнес-логика не знает, откуда пришел запрос и где хранятся данные.
```

---

## 4. Как этот подход решает проблему

### 4.1. Бизнес-правила выносятся в доменный слой

Правила расчета скидки, проверки права на льготы и обработки заявок нужно вынести из контроллеров и технических сервисов в отдельный доменный или прикладной слой.

Например:

```text
DiscountPolicy
BenefitEligibilityPolicy
ApplicationProcessingService
```

Эти компоненты должны работать с бизнес-понятиями:

```text
Student
Application
Benefit
Discount
Course
Payment
```

А не с HTTP-запросами, SQL-строками или ORM-моделями.

### 4.2. Контроллеры становятся тонкими

Контроллер не должен содержать бизнес-правила.

Его задача:

1. принять HTTP-запрос;
2. провалидировать технический формат входных данных;
3. преобразовать request в команду или DTO;
4. вызвать use case;
5. вернуть HTTP-ответ.

Пример целевого потока:

```text
HTTP Controller
        |
        v
CalculateDiscountUseCase
        |
        v
DiscountPolicy
```

Контроллер не рассчитывает скидку сам. Он только вызывает сценарий использования.

### 4.3. Работа с БД скрывается за репозиториями

Бизнес-логика не должна выполнять SQL-запросы напрямую и не должна зависеть от ORM.

Вместо этого вводятся интерфейсы:

```text
StudentRepository
ApplicationRepository
BenefitRepository
```

Use case зависит от интерфейса:

```text
ApplicationRepository
```

А конкретная реализация находится в инфраструктурном слое:

```text
SqlApplicationRepository
OrmApplicationRepository
```

Если схема БД или ORM изменится, меняется только инфраструктурная реализация репозитория. Бизнес-логика остается прежней.

### 4.4. Внешние API изолируются через адаптеры

Если система обращается к внешнему API, бизнес-логика не должна работать с его SDK или HTTP-клиентом напрямую.

Нужно ввести внутренний интерфейс:

```text
ExternalStudentStatusProvider
```

А реализацию вынести в адаптер:

```text
ExternalStudentStatusApiAdapter
```

Use case работает только с интерфейсом. Если внешний API изменится, нужно переписать адаптер, а не бизнес-правила.

### 4.5. Бизнес-правила становятся тестируемыми

После отделения бизнес-логики от инфраструктуры правила можно тестировать изолированно.

Например, расчет скидки можно проверить без HTTP-сервера и без БД:

```text
Given: студент имеет льготу
And: курс стоит 10 000
When: рассчитывается скидка
Then: итоговая цена равна 7 000
```

Для такого теста не нужна реальная БД. Достаточно создать объекты предметной области в памяти.

## 5. Возможная целевая структура системы

```text
src/
  domain/
    Student
    Application
    Benefit
    Discount
    DiscountPolicy
    BenefitEligibilityPolicy

  application/
    CalculateDiscountUseCase
    CheckBenefitEligibilityUseCase
    ProcessApplicationUseCase
    ports/
      StudentRepository
      ApplicationRepository
      BenefitRepository
      ExternalStudentStatusProvider

  infrastructure/
    persistence/
      SqlStudentRepository
      OrmApplicationRepository
    external/
      ExternalStudentStatusApiAdapter

  presentation/
    http/
      ApplicationController
      DiscountController
```

Смысл структуры:

- `domain` содержит бизнес-сущности и бизнес-правила;
- `application` содержит сценарии использования;
- `ports` содержит интерфейсы, через которые бизнес-логика обращается наружу;
- `infrastructure` содержит технические реализации;
- `presentation` содержит HTTP-контроллеры.

---

## 6. Сравнение текущей и целевой архитектуры

| Критерий | Текущая архитектура | Целевая архитектура |
|---|---|---|
| Где находятся бизнес-правила | В контроллерах и сервисах, связанных с HTTP, ORM и SQL | В доменном и прикладном слоях |
| Зависимость бизнес-логики от БД | Прямая зависимость от ORM, SQL и схемы БД | Зависимость только от интерфейсов репозиториев |
| Зависимость от внешних API | Прямая зависимость от конкретного API или SDK | Через внутренние порты и адаптеры |
| Тестирование бизнес-правил | Сложное, требует инфраструктуры | Простое, можно тестировать изолированно |
| Изменение схемы БД | Может затронуть бизнес-логику | Затрагивает только инфраструктурный слой |
| Изменение HTTP API | Может затронуть бизнес-логику | Затрагивает в основном presentation layer |
| Сопровождение | Сложное, изменения расползаются по системе | Более локализованное и предсказуемое |

---

## 7. За счет чего подход решает проблему

Подход чистой архитектуры решает проблему за счет трех основных механизмов.

### 7.1. Разделение слоев

Каждый слой отвечает за свою задачу:

```text
Контроллеры — за HTTP
Use Cases — за сценарии системы
Domain — за бизнес-правила
Repositories / Adapters — за технические детали
```

Бизнес-правила перестают быть размазанными по контроллерам и SQL-запросам.

### 7.2. Инверсия зависимостей

Вместо зависимости бизнес-логики от ORM и внешних API вводятся интерфейсы.

Неправильно:

```text
BusinessService -> ORM -> SQL -> Database
```

Правильно:

```text
UseCase -> Repository interface
Infrastructure Repository -> ORM -> SQL -> Database
```

Use case знает только о контракте, но не знает, как именно данные получаются.

### 7.3. Изоляция инфраструктуры

HTTP, ORM, SQL и внешние API становятся заменяемыми деталями.

Если меняется база данных, меняется реализация репозитория.  
Если меняется внешний API, меняется адаптер.  
Если меняется HTTP-контракт, меняется контроллер или mapper.  
Бизнес-правила остаются стабильными.

---

## 8. Краткий вывод

В текущей системе архитектурно неудачно то, что бизнес-правила смешаны с техническими деталями: HTTP-слоем, ORM, SQL-запросами, схемой базы данных и внешними API. Из-за этого изменение инфраструктуры приводит к изменению бизнес-логики, а поддержка и тестирование становятся сложными.

Уместный подход — **чистая архитектура / Ports and Adapters / Hexagonal Architecture**. Он предполагает, что бизнес-логика находится в центре системы, а инфраструктура подключается к ней через интерфейсы и адаптеры.

Этот подход решает проблему за счет:

- отделения бизнес-правил от контроллеров;
- вынесения сценариев в use case слой;
- сокрытия БД за репозиториями;
- изоляции внешних API через адаптеры;
- зависимости бизнес-логики от абстракций, а не от технических реализаций;
- возможности тестировать бизнес-правила без HTTP, ORM и реальной БД.

В результате система становится проще для сопровождения, устойчивее к изменениям требований и технической инфраструктуры, а бизнес-правила можно развивать независимо от способов хранения данных и внешних интеграций.
