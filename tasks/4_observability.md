# Задача 4. Повышение наблюдаемости контейнерной системы

## 1. Краткий анализ проблемы

Приложение работает в контейнерах на нескольких узлах. Периодически часть контейнеров перезапускается, а время ответа системы возрастает. Команда узнает о проблемах в основном от пользователей, а не из собственных инструментов.

Это означает, что в системе недостаточно развита наблюдаемость.

Текущие проблемы:

1. **Логи хранятся локально внутри контейнеров.**  
   После перезапуска контейнера часть логов теряется или становится труднодоступной.

2. **Нет централизованной системы сбора логов.**  
   Команда не может быстро посмотреть, что происходило во всех контейнерах и на всех узлах в момент инцидента.

3. **Нет единой картины по метрикам.**  
   Не видно, какие контейнеры перезапускались, где росло потребление CPU/RAM, где увеличивалась задержка ответа и где появлялись ошибки.

4. **Нет надежных алертов.**  
   Команда узнает о деградации по сообщениям пользователей, а не по автоматическим уведомлениям.

5. **Нет сквозной диагностики запросов.**  
   Если система состоит из нескольких компонентов, сложно понять, на каком участке возникла задержка.

6. **Нет достаточной информации для разбора инцидентов.**  
   После перезапуска контейнеров важные данные могут быть потеряны, поэтому восстановить причину сбоя сложно.

Главная архитектурная проблема: система работает в контейнерной среде, но не имеет полноценного контура observability: централизованных логов, метрик, трассировки, алертов и практик разбора инцидентов.

## 3. Централизованный сбор логов

### Что добавить

Нужно вынести логи из контейнеров во внешнюю централизованную систему.

Подходящие инструменты:

- **ELK / EFK stack**:
  - Elasticsearch или OpenSearch — хранение и поиск логов;
  - Logstash или Fluent Bit / Fluentd — сбор и доставка логов;
  - Kibana / OpenSearch Dashboards — просмотр и анализ логов.

Либо альтернативный стек:

- **Grafana Loki + Promtail / Fluent Bit**;
- **Grafana** для просмотра логов.

### Какую проблему решает

Сейчас логи находятся внутри контейнеров. Это плохо, потому что контейнеры являются временными сущностями. При перезапуске контейнера логи могут быть потеряны или стать труднодоступными.

Централизованный сбор логов решает следующие проблемы:

| Проблема | Решение |
|---|---|
| Логи теряются после перезапуска контейнера | Логи отправляются во внешнее хранилище до удаления контейнера |
| Невозможно быстро посмотреть логи всех контейнеров | Все логи доступны в одном интерфейсе |
| Сложно найти причину инцидента | Можно искать по времени, сервису, уровню ошибки, request ID |
| Логи разбросаны по разным узлам | Логи агрегируются централизованно |

### Как должно быть

Приложения должны писать логи в `stdout` / `stderr`, а агент на узле должен собирать эти логи и отправлять их в централизованное хранилище.

```text
Контейнеры
   |
   | stdout / stderr
   v
Log collector на узле
   |
   v
Централизованное хранилище логов
   |
   v
Интерфейс поиска и анализа логов
```

## 4. Структурированные логи

### Что добавить

Логи нужно писать в структурированном формате, например JSON.

Пример логической структуры записи:

```json
{
  "timestamp": "2026-05-23T12:00:00Z",
  "level": "ERROR",
  "service": "booking-service",
  "container_id": "abc123",
  "node": "node-1",
  "request_id": "req-789",
  "user_id": "user-42",
  "operation": "create_reservation",
  "message": "Failed to create reservation",
  "error": "Database timeout"
}
```

### Какую проблему решает

Неструктурированные текстовые логи сложно фильтровать и анализировать. Структурированные логи позволяют быстро искать события по полям:

- сервис;
- контейнер;
- узел;
- уровень ошибки;
- request ID;
- пользователь;
- операция;
- тип исключения.

Это ускоряет диагностику инцидентов.

## 5. Метрики системы

### Что добавить

Нужно внедрить сбор метрик.

Подходящие инструменты:

- **Prometheus** — сбор и хранение временных рядов метрик;
- **Grafana** — визуализация метрик;
- **node_exporter** — метрики узлов;
- **cAdvisor** или container exporter — метрики контейнеров;
- runtime/application exporter — метрики приложения.

### Какие метрики нужны

#### Метрики контейнеров

- количество рестартов контейнеров;
- CPU usage;
- memory usage;
- memory limit;
- OOMKilled;
- filesystem usage;
- network in/out;
- количество активных контейнеров;
- состояние контейнера.

#### Метрики приложения

- RPS;
- среднее время ответа;
- p95 / p99 latency;
- error rate;
- количество 4xx и 5xx ответов;
- количество таймаутов;
- длина очередей, если они есть;
- время обработки запросов;
- количество активных соединений.

#### Метрики инфраструктуры

- CPU узла;
- RAM узла;
- disk usage;
- disk I/O;
- network latency;
- network errors;
- load average.

### Какую проблему решает

Сейчас команда видит только последствия: пользователи жалуются, что система медленно работает. Метрики позволяют увидеть деградацию раньше.

Например:

| Признак | Что он может означать |
|---|---|
| Растет p95/p99 latency | Система деградирует, пользователи скоро заметят проблему |
| Растет количество 5xx | Возникают ошибки на стороне сервера |
| Растут рестарты контейнеров | Контейнеры падают или убиваются |
| Появился OOMKilled | Контейнеру не хватает памяти |
| CPU постоянно близок к лимиту | Контейнеру не хватает вычислительных ресурсов |
| Растет очередь запросов | Сервис не успевает обрабатывать нагрузку |

## 6. Дашборды

### Что добавить

Нужно создать дашборды в Grafana или аналогичном инструменте.

Минимальный набор дашбордов:

1. **Общее состояние системы**
   - RPS;
   - error rate;
   - p95/p99 latency;
   - количество активных контейнеров;
   - количество рестартов.

2. **Состояние контейнеров**
   - CPU;
   - RAM;
   - OOMKilled;
   - restarts;
   - throttling;
   - network usage.

3. **Состояние узлов**
   - CPU узлов;
   - RAM;
   - диск;
   - сеть;
   - load average.

4. **Состояние конкретного сервиса**
   - latency;
   - ошибки;
   - dependency latency;
   - внутренние бизнес-метрики.

5. **Инцидентный дашборд**
   - последние ошибки;
   - последние рестарты;
   - проблемные узлы;
   - сервисы с максимальной задержкой.

### Какую проблему решает

Дашборды дают команде единую картину состояния системы.

Без дашбордов команда анализирует проблему вручную: заходит на узлы, смотрит контейнеры, ищет логи, сравнивает время событий. Это долго и ненадежно.

С дашбордами можно сразу увидеть:

- когда началась деградация;
- какой сервис пострадал;
- на каком узле проблема;
- были ли рестарты контейнеров;
- росли ли ошибки;
- не закончилась ли память;
- изменилась ли нагрузка.

## 7. Алерты

### Что добавить

Нужно настроить автоматические уведомления о проблемах.

Подходящие инструменты:

- **Prometheus Alertmanager**;
- Grafana Alerting;
- Opsgenie / PagerDuty / Slack / Telegram / email-интеграции.

### На что настраивать алерты

Примеры важных алертов:

| Алерт | Условие |
|---|---|
| High error rate | Доля 5xx выше допустимого порога |
| High latency | p95 или p99 latency выше нормы |
| Container restarts | Количество рестартов контейнера выросло |
| OOMKilled | Контейнер был убит из-за нехватки памяти |
| Service down | Нет живых экземпляров сервиса |
| Node unavailable | Узел недоступен |
| Disk almost full | Диск заполнен выше порога |
| CPU saturation | CPU долго находится около лимита |
| Memory saturation | RAM близка к лимиту |
| No logs from service | Сервис перестал отправлять логи |
| No metrics from service | Сервис перестал отдавать метрики |

### Какую проблему решает

Сейчас команда узнает о проблеме от пользователей. Это означает, что обнаружение инцидента происходит слишком поздно.

Алерты позволяют узнать о деградации до массовых жалоб.

Например, если p99 latency вырос до критического значения, команда должна получить уведомление сразу, даже если часть пользователей еще не написала в поддержку.

## 8. Health checks: liveness и readiness

### Что добавить

Для контейнеров нужно настроить проверки состояния:

1. **Liveness probe**  
   Проверяет, живо ли приложение. Если приложение зависло, контейнер можно перезапустить.

2. **Readiness probe**  
   Проверяет, готово ли приложение принимать трафик. Если приложение еще запускается или временно не готово, балансировщик не должен отправлять на него запросы.

3. **Startup probe**  
   Нужна для приложений, которые долго стартуют. Позволяет не убивать контейнер слишком рано во время запуска.

### Какую проблему решает

Если контейнер формально запущен, это не всегда означает, что приложение внутри него готово работать.

Без readiness check балансировщик может отправлять трафик в контейнер, который:

- еще не подключился к БД;
- еще не прогрел кеш;
- еще не загрузил конфигурацию;
- находится в деградированном состоянии.

Без корректного liveness check зависший контейнер может оставаться в системе и продолжать принимать запросы.

Health checks позволяют быстрее исключать неисправные экземпляры из обработки трафика.

## 9. Distributed tracing

### Что добавить

Нужно внедрить распределенную трассировку.

Подходящие инструменты:

- **OpenTelemetry** — стандарт для сбора traces, metrics и logs;
- **Jaeger**;
- **Zipkin**;
- **Tempo**.

### Какую проблему решает

Если запрос проходит через несколько сервисов, по обычным логам сложно понять, где именно возникла задержка.

Distributed tracing позволяет увидеть полный путь запроса:

```text
HTTP request
   |
   v
API Gateway: 10 ms
   |
   v
Service A: 40 ms
   |
   v
Database query: 800 ms
   |
   v
Service B: 120 ms
```

Это помогает быстро определить, где именно возникла деградация:

- в приложении;
- в БД;
- во внешнем API;
- в сети;
- в конкретном сервисе;
- в конкретном SQL-запросе.

Для текущей задачи это особенно важно, потому что время ответа системы заметно возрастает, но команда не имеет единой картины причин.

## 10. Correlation ID / Request ID

### Что добавить

Каждому входящему запросу нужно присваивать уникальный идентификатор:

```text
X-Request-ID
```

или

```text
X-Correlation-ID
```

Этот идентификатор должен передаваться между сервисами и попадать:

- в логи;
- в трассировки;
- в сообщения очередей;
- в ошибки;
- в ответы API при необходимости.

### Какую проблему решает

Correlation ID позволяет связать все события по одному пользовательскому запросу.

Без него команда видит разрозненные логи:

```text
service-a: timeout
service-b: request failed
database: slow query
```

С correlation ID можно найти всю цепочку:

```text
request_id=req-123
```

и посмотреть:

- где запрос начался;
- через какие сервисы прошел;
- где возникла задержка;
- какая ошибка была первопричиной.

## 11. Error tracking

### Что добавить

Для ошибок приложения можно добавить систему error tracking.

Подходящие инструменты:

- **Sentry**;
- Rollbar;
- Bugsnag.

### Какую проблему решает

Логи показывают поток событий, но error tracking удобнее для анализа исключений приложения.

Он позволяет видеть:

- группировку одинаковых ошибок;
- stack trace;
- частоту возникновения ошибки;
- версию приложения;
- окружение;
- affected users;
- момент появления ошибки после релиза.

Это ускоряет анализ ошибок, особенно если контейнеры перезапускаются и локальные логи теряются.

## 12. Практики хранения и retention

### Что добавить

Нужно определить правила хранения данных наблюдаемости:

- сколько хранить логи;
- сколько хранить метрики;
- сколько хранить traces;
- какие данные хранить подробно;
- какие данные агрегировать;
- какие данные удалять.

Пример:

```text
Логи ошибок: 30–90 дней
Обычные application logs: 7–30 дней
Метрики высокой детализации: 7–14 дней
Агрегированные метрики: 6–12 месяцев
Traces: 3–14 дней
```

### Какую проблему решает

Без retention-политики система наблюдаемости может быстро занять слишком много места. Или наоборот, данные будут удаляться слишком рано, и команда не сможет разобрать инцидент.

## 13. Практики incident response

### Что добавить

Инструменты сами по себе недостаточны. Нужны практики работы с инцидентами:

1. **Определить SLI и SLO**
   - SLI: latency, availability, error rate;
   - SLO: например, 99.9% успешных запросов и p95 latency менее заданного порога.

2. **Настроить алерты по симптомам, а не только по причинам**
   - плохо: алерт только на CPU;
   - лучше: алерт на рост 5xx, latency и недоступность сервиса.

3. **Создать runbook**
   - что делать при росте latency;
   - что делать при рестартах контейнеров;
   - что делать при OOMKilled;
   - где смотреть логи;
   - какие дашборды открыть первыми.

4. **Вести postmortem после серьезных инцидентов**
   - что произошло;
   - когда началось;
   - как обнаружили;
   - почему алерты не сработали;
   - какие действия предотвратят повторение.

5. **Связывать релизы с метриками и ошибками**
   - после деплоя должно быть видно, выросли ли ошибки;
   - Sentry или аналог должен показывать, в какой версии появилась ошибка.

### Какую проблему решает

Команда перестает действовать хаотично во время инцидента. Разбор становится системным и воспроизводимым.

## 14. Итоговая таблица: элемент наблюдаемости и решаемая проблема

| Элемент | Что добавить | Какую проблему решает |
|---|---|---|
| Централизованный сбор логов | ELK/EFK, OpenSearch, Loki, Fluent Bit, Promtail | Логи не теряются после перезапуска контейнеров и доступны из единого места |
| Структурированные логи | JSON-логи с полями `service`, `level`, `request_id`, `container_id`, `node` | Ускоряют поиск причин инцидента и фильтрацию событий |

| Дашборды | Grafana dashboards | Дают единую картину состояния системы |
| Алерты | Alertmanager, Grafana Alerting, Slack/Telegram/email | Команда узнает о проблеме раньше пользователей |
| Health checks | Liveness, readiness, startup probes | Неисправные или неготовые контейнеры исключаются из обработки трафика |
| Distributed tracing | OpenTelemetry, Jaeger, Tempo, Zipkin | Позволяет понять, где именно в цепочке запроса возникла задержка |
| Correlation ID / Request ID | Передача идентификатора запроса между сервисами | Связывает логи, traces и ошибки в единую цепочку |
| Error tracking | Sentry или аналог | Помогает анализировать исключения, stack trace и ошибки после релизов |
| Retention policy | Правила хранения логов, метрик и traces | Данные не теряются слишком рано и не переполняют хранилище |
| Runbooks | Инструкции по действиям при типовых инцидентах | Ускоряют реакцию команды и снижают хаос при авариях |
| Postmortem | Разбор инцидентов после восстановления | Помогает устранять первопричины, а не только симптомы |

## 16. Краткий вывод

В текущей системе проблема не только в том, что контейнеры периодически перезапускаются. Главная проблема в том, что команда не видит состояние системы достаточно рано и достаточно полно. Логи хранятся локально в контейнерах, метрики и признаки деградации не собраны в единую картину, а алерты не позволяют обнаруживать проблему до жалоб пользователей.

Для повышения наблюдаемости нужно добавить:

- централизованный сбор и хранение логов;
- структурированные логи;
- сбор технических и прикладных метрик;
- дашборды;
- автоматические алерты;
- liveness/readiness/startup health checks;
- distributed tracing;
- correlation ID;
- error tracking;
- retention-политику;
- runbooks и postmortem-практики.
